# Arkandia — API Pública v1

Documentação da API pública do Arkandia. Use pra integrar bots Discord, dashboards externos, ferramentas de comunidade etc.

---

## Visão Geral

- **Base URL:** `https://www.ernas.com.br/api/public/v1`
- **Auth:** header `X-API-Key` + scopes granulares por operação
- **Métodos:** `GET` (read) e `POST` (writes em libras e inventário — exigem scope + idempotency)
- **Formato:** JSON
- **CORS:** liberado pra qualquer origem (`*`)
- **Rate limit:** 120 req/min/key pra qualquer chamada + **10 writes/min/key** adicional pra POSTs
- **Versionamento:** `/v1/` — mudanças breaking só em `/v2/`
- **Runas:** **não há endpoint nem scope** pra mexer em Runas por design (cash real, MercadoPago no pipeline). Só painel Dev/GM.

---

## Autenticação

Toda request precisa enviar o header `X-API-Key` com a key fornecida.

```bash
curl -H "X-API-Key: ark_pub_xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx" \
     https://www.ernas.com.br/api/public/v1/rankings/poder?limit=10
```

### Erros de auth

| Status | Significado |
|-------:|-------------|
| `401` | Header `X-API-Key` ausente, key inválida, revogada ou em formato errado |
| `403` | Key válida mas **sem scope** necessário pra essa operação (ex: tentou debitar Libras com key que só tem `read`) |

```json
{ "error": "Missing X-API-Key header" }
{ "error": "Invalid API key" }
{ "error": "Missing required scope: currency:libras:write" }
```

---

## Scopes (permissões)

Cada API key tem um array de **scopes** que define o que ela pode fazer. Toda key recebe `read` automaticamente — é o mínimo pra qualquer GET funcionar. Writes exigem scope dedicado, escolhido na criação da key pelo Dev.

| Scope | Permite |
|---|---|
| `read` | **Default obrigatório.** Todos os GETs (catálogos, personagens, rankings, eventos, missões). |
| `inventory:write` | POSTs `/personagens/[id]/inventario/{adicionar,remover}`. Cap **100 unidades/op**. |
| `currency:libras:write` | POSTs `/personagens/[id]/libras/{creditar,debitar}`. Cap **100.000 Libras/op**. |

**Por que Runas não tem scope?** Runas são cash real (premium, MercadoPago no pipeline). API externa nunca toca em Runas por design — só painel Dev ou GM dentro do site. Bot Discord que quiser dar Runas pra alguém precisa cadastrar via painel manualmente.

Pedir nova key com scopes específicos é responsabilidade do Dev — peça especificamente o que precisa.

---

## Rate Limit

Limit **duplo**, ambos sliding window:

| Limiter | Limite | Aplica em |
|---|---|---|
| Geral | 120 req/min/key | Qualquer chamada (GET ou POST) |
| Write | **+ 10 req/min/key** | POSTs (additional sobre o geral — write conta nos 2) |

A defesa dupla limita o blast radius se uma key vazar: mesmo com key roubada, o atacante consegue no máximo **10 operações mutantes por minuto** antes de bater no 429.

Headers de resposta:
- `X-RateLimit-Limit: 120`
- `X-RateLimit-Remaining: 87`
- `X-RateLimit-Reset: 1715798400000` (timestamp ms)
- `X-RateLimit-Limit-Write: 10` (só em POSTs)
- `X-RateLimit-Remaining-Write: 7` (só em POSTs)

Quando excedido:
```json
{ "error": "Rate limit exceeded. Limit: 120 requests per minute." }
{ "error": "Write rate limit exceeded. Limit: 10 write operations per minute." }
```
- Status: `429 Too Many Requests`
- Header: `Retry-After: 30` (segundos pra tentar de novo)

Requests **sem header `X-API-Key`** caem num rate limit por IP (60/min) — então não dá pra fazer scrapping antes de receber a key.

## Idempotency (POSTs)

Toda mutação (POST) **exige** o header `Idempotency-Key` com um **UUID v4** único pra cada operação distinta.

```
Idempotency-Key: 9f2b1c3d-4e5f-6a7b-8c9d-0e1f2a3b4c5d
```

### Por que é obrigatória

Você credita 500 Libras pra um jogador. O servidor processa, mas o request **falha em responder** (timeout, conexão caiu, 5xx temporário). Seu bot tem retry automático. **Sem idempotency, o jogador receberia 1000 Libras** em vez de 500. Com retry exponencial, vira 1500, 2000.

Com idempotency, o servidor guarda `(key_id, idempotency_key) → response_json`. Se o mesmo UUID chegar de novo, **devolve a resposta cacheada sem re-executar a operação**. Cliente recebe a mesma resposta que recebeu da primeira vez, sem dobrar o crédito.

### Como gerar o UUID

```js
// Node.js 14.17+
import { randomUUID } from 'crypto'
const idempotencyKey = randomUUID()

// Browser moderno
const idempotencyKey = crypto.randomUUID()
```

### Quando reusar vs gerar novo

- **Mesma operação lógica** (retry de uma falha) → **reuse o mesmo UUID**. Esse é o ponto.
- **Operação diferente** (segunda compra do mesmo jogador) → **gere UUID novo**, senão o servidor responde com o resultado da primeira compra e ignora a segunda.

### Resposta cacheada

Retry com mesmo UUID retorna o mesmo body da primeira resposta, mas com flag `idempotency_replay: true`:

```json
{ "ok": true, "novo_saldo": 1500, "valor_creditado": 500, "idempotency_replay": true }
```

### Quando o cache fica preenchido

| Resposta inicial | Cacheada? | Retry devolve |
|---|---|---|
| 200 sucesso | ✓ | 200 + `idempotency_replay: true` |
| 400 body inválido | ✓ | 400 cacheado. Pra body novo, **use Idempotency-Key novo** |
| 402 saldo/quantidade insuficiente | ✓ | 402 cacheado. Pra retry após resolver, **use Idempotency-Key novo** |
| 403 anti-IDOR | ✓ | 403 cacheado |
| 404 não encontrado | ✓ | 404 cacheado |
| 409 item equipado / race | ✓ | 409 cacheado |
| 500 erro de servidor | ✗ libera | Próximo retry re-executa |
| Exception não tratada | ✗ libera | Próximo retry re-executa |

Lógica: **4xx é semântico** (o request foi entendido e rejeitado) — cachear evita re-executar débito duplicado se cliente fizer retry achando que foi erro de rede. **5xx é erro temporário** (Postgres caiu, Vercel hiccup) — liberar permite retry com mesmo Idempotency-Key sem ficar travado.

### Status `409 in_flight` (duas requests paralelas)

Se duas requests com o **mesmo Idempotency-Key** chegam paralelas (raro mas possível com retry agressivo), a primeira reserva a chave e processa. A segunda recebe:

```
HTTP 409 Conflict
Retry-After: 2

{ "error": "Request com mesma Idempotency-Key em andamento, retry em alguns segundos" }
```

Cliente deve aguardar 2-3s e fazer retry com o **mesmo UUID** — vai pegar a resposta cacheada da primeira execução.

### Validade

Cache mantido por **24h** (depois o cron purga). Retry após 24h re-executa a operação — então retries longos devem usar UUID novo.

### Sem header → 400

```json
{ "error": "Idempotency-Key header obrigatório (UUID)" }
```

## Paginação

Endpoints de listagem aceitam `limit` e `offset`. Limites por endpoint:

| Endpoint | Default | Max |
|----------|--------:|----:|
| `/personagens/buscar` | 20 | 50 |
| `/rankings/poder` | 20 | 100 |
| `/rankings/nivel` | 20 | 100 |
| `/rankings/guildas` | 10 | 50 |
| `/rankings/arena` | 20 | 100 |
| `/skills` | 50 | 200 |
| `/itens` | 50 | 200 |
| `/pergaminhos` | 50 | 100 |
| `/maestrias` | 50 | 100 |
| `/npcs` | 50 | 100 |
| `/bestiario` | 50 | 100 |

Endpoints sem `limit/offset` (`/eventos/ativos`, `/missoes/abertas`, `/guildas/:id`, `/personagens/:nomeOuId`) retornam o conjunto completo.

Resposta paginada padrão:
```json
{ "total": 152, "limit": 50, "offset": 0, "skills": [ ... ] }
```

**⚠ Atenção — `build_skills` vs `skills_adquiridas`:**
- **`build_skills`** = skills **EQUIPADAS** na build do personagem agora (max 8: 1 racial + 7 livres). Slots vazios são omitidos. **É isso que você usa pra mostrar "skills equipadas" num bot/UI.**
- **`build`** = mesmas skills mas como **IDs brutos** por slot (`slot_racial`, `slot_1`, ..., `slot_7`). Útil pra correlacionar com catálogo. Slots vazios = `null`.
- **`skills_adquiridas`** = **acervo completo** — todas as skills que o personagem aprendeu na vida (de pergaminhos despertados, maestrias dominadas, compradas da classe, encantamentos de itens). Pode ser bem maior que `build_skills` (jogador tem várias skills mas só pode equipar 8). **NÃO é "equipadas"** — bug clássico de quem assume que sim.

**⚠ Atenção — `inventario` vs `equipamento`:**
- **`inventario`** = **TODOS** os itens em posse do personagem (mochila + equipados). Cada row tem `id` (que é o `inventario_id` necessário pra `POST /personagens/:id/inventario/remover`), `quantidade` total, `reservado` (unidades comprometidas em marketplace ou negociações P2P) e `disponivel` (= `quantidade - reservado`, único valor seguro pra remoção/transferência). Ordenado por `criado_em DESC` (mais recente primeiro).
- **`equipamento`** = view filtrada (apenas itens com `equipado=true`), formato achatado mais simples. Mantido pra compatibilidade com bots antigos. **Novos consumers devem preferir `inventario`** — tem todas as informações que `equipamento` tem + mais.
- Armas e armaduras são **instâncias únicas**: cada unidade vira sua própria row em `inventario` com `quantidade=1` (mesmo que o jogador tenha 2 "Lâminas do Trovão" idênticas, são 2 rows com `id` distintos). Consumíveis e materiais empilham em uma única row com `quantidade > 1`.
- `disponivel` é o valor que importa pra remoção. Se `quantidade=17` e `reservado=5` (o jogador tem 5 lingotes anunciados no marketplace), só `12` podem ser removidos via API antes de quebrar a reserva.
- Timestamp da row é `obtido_em` (nome interno da coluna no banco). O alias `criado_em` é retornado como sinônimo pra clientes que assumiram o nome padrão — apontam pro mesmo valor.

**Saldo de moedas:**
- **`libras`** (campo na raiz) — saldo em Libras (moeda do RPG, comercializável entre jogadores no marketplace). Lido de `profiles.libras` (saldo é por conta auth, não por personagem). Valor inteiro, sem decimais.
- **Runas não são expostas** na API pública por design. Runas são cashable (BRL → Runas via MercadoPago) e ficam fora do escopo de read pública. Painel Dev/GM é o único caminho pra inspecionar saldo de runas.

#### `GET /personagens/habbo/:nick`

Resolve o personagem **ativo** do user dono do nick Habbo informado. Útil pra bot Discord que recebe nick do Habbo e quer puxar a ficha sem precisar saber o nome do personagem.

**Path params:**
- `nick` — Habbo nick exato (case-insensitive). 1-25 chars, alfanumérico + `_`, `.`, `-`.

**Resposta:** mesmo payload do `/personagens/:nomeOuId`, com campo extra:
```json
{
  "id": "...",
  "nome": "Aragorn",
  "...": "...",
  "resolvido_por": { "tipo": "habbo_nick", "valor": "kurtprod" }
}
```

**Erros:**
- `400` se nick tem formato inválido
- `404` se nick não cadastrado, ou user existe mas não tem personagem ativo

#### `GET /personagens/discord/:idOuUsername`

Resolve o personagem **ativo** do user que fez login via Discord OAuth. Aceita 2 formatos:

- **Discord user ID** (snowflake numérico, 17–19 dígitos): `/personagens/discord/289927100465676288`
- **Discord username**: `/personagens/discord/sowjetdream` ou `/personagens/discord/sowjetdream%230`

**Discord ID é mais estável** (não muda nunca) — usar como chave primária no bot. Username muda se o user trocar; aceita com ou sem discriminator (Discord migrou pra usernames únicos com `#0`).

**Path params:**
- `idOuUsername` — snowflake numérico OU username (2–32 chars + `#NNNN` opcional)

**Resposta:** mesmo payload do `/personagens/:nomeOuId`, com campo extra:
```json
{
  "id": "...",
  "nome": "Aragorn",
  "...": "...",
  "resolvido_por": { "tipo": "discord_id", "valor": "289927100465676288" }
}
```
(`tipo` é `"discord_id"` se foi snowflake, `"discord_username"` se foi username)

**Erros:**
- `400` se identifier tem formato inválido
- `404` se Discord ID/username não cadastrado, user não logou via Discord, ou não tem personagem ativo

#### `GET /itens?categoria=&raridade=&grau=&busca=&so_assinatura=&limit=&offset=`

Catálogo de itens.

**Query params:**
- `categoria` — `arma` | `armadura` | `acessorio` | `consumivel` | `material` | `insignia` | `chave` | `maestria` | `encantamento`
- `raridade` — `comum` | `raro` | `epico` | `lendario` | `mitico`

- `busca` — substring

## Mutações (POST)

Todos os endpoints abaixo:
- Exigem `X-API-Key` com o scope listado
- Exigem `Idempotency-Key: <uuid>` no header
- Logam em `transacoes_libras` (no caso de Libras) com `tipo='api_publica'`, `descricao` prefixada com `[API <nome-da-key>]` e `referencia_id = api_keys.id`
- Aparecem no audit log (`api_publica_audit`) com hash sha256 do payload (plaintext nunca armazenado)
- Contam contra `+ 10 writes/min/key` adicional

### Libras

#### `POST /personagens/:id/libras/creditar`

Credita Libras no saldo do dono do personagem. Atomic via RPC Postgres (sem race condition).

**Scope:** `currency:libras:write`
**Cap:** `valor` máximo 100.000 por chamada

**Path params:**
- `id` — UUID do personagem (não nome — `id` aqui é estável)

**Headers:**
```
X-API-Key: ark_pub_xxx
Content-Type: application/json
Idempotency-Key: <uuid-v4>
```

**Body:**
```json
{ "valor": 500, "descricao": "Recompensa de sessão #142" }
```

**Resposta `200`:**
```json
{
  "ok": true,
  "personagem_id": "550e8400-...",
  "personagem_nome": "Aragorn",
  "valor_creditado": 500,
  "novo_saldo": 12450
}
```

**Erros:**
- `400` body inválido (valor fora do range 1–100.000, descricao vazia/muito longa, etc), Idempotency-Key ausente ou não-UUID
- `401` X-API-Key ausente/inválida
- `403` key sem scope `currency:libras:write`
- `404` personagem não encontrado ou inativo
- `429` rate limit (geral ou write)

---

#### `POST /personagens/:id/libras/debitar`

Debita Libras do saldo. **Atomic + bloqueio de saldo negativo** no RPC — se o jogador não tem saldo suficiente, retorna `402` sem fazer nada.

**Scope:** `currency:libras:write`
**Cap:** `valor` máximo 100.000 por chamada

**Body:**
```json
{ "valor": 150, "descricao": "Custo de inscrição em torneio" }
```

**Resposta `200`:** mesma estrutura do creditar (com `valor_debitado` em vez de `valor_creditado`).

**Resposta `402 Payment Required`** (saldo insuficiente):
```json
{ "error": "Saldo de Libras insuficiente", "personagem_id": "550e8400-..." }
```

A transação é logada em `transacoes_libras` com `valor` **negativo** (convenção do projeto).

### Inventário

#### `POST /personagens/:id/inventario/adicionar`

Adiciona N unidades de um item ao inventário. **Categoria-aware**: armas/armaduras (categorias de instância única) viram **N rows separadas** com `quantidade=1` cada, pra preservar estado individual (encantamentos, grau, etc). Demais categorias stackam normalmente.

**Scope:** `inventory:write`
**Cap:** `quantidade` máxima 100 por chamada

Aceita **`item_id` (UUID)** OU **`slug` (string)** — exatamente um dos dois, não ambos.

**Body (com item_id):**
```json
{ "item_id": "550e8400-...", "quantidade": 1 }
```

**Body (com slug):**
```json
{ "slug": "pedra-refinamento", "quantidade": 5 }
```

**Resposta `200`:**
```json
{
  "ok": true,
  "personagem_id": "...",
  "item_id": "...",
  "item_nome": "Pedra de Refinamento",
  "item_slug": "pedra-refinamento",
  "quantidade_adicionada": 5
}
```

**Erros:**
- `400` body inválido (envia ambos `item_id` e `slug`, quantidade fora de 1–100, etc), Idempotency-Key ausente
- `403` key sem scope `inventory:write`
- `404` personagem não encontrado, ou item não existe no catálogo

---

#### `POST /personagens/:id/inventario/remover`

Remove N unidades de **uma row específica** do inventário. Exige `inventario_id` (não `item_id`) porque armas/armaduras têm múltiplas rows com mesmo `item_id` (instâncias únicas) e o caller precisa escolher qual.

**Como descobrir o `inventario_id`:** consulte a ficha completa via `GET /personagens/:nomeOuId` — o array `inventario` traz cada row com o campo `id`, que é exatamente o `inventario_id` esperado aqui. Use o `disponivel` (= `quantidade - reservado`) como limite seguro pra remoção.

**Scope:** `inventory:write`
**Cap:** `quantidade` máxima 100 por chamada

**Body:**
```json
{ "inventario_id": "a3f4...", "quantidade": 1 }
```

**Resposta `200`:**
```json
{
  "ok": true,
  "personagem_id": "...",
  "inventario_id": "a3f4...",
  "item_id": "...",
  "quantidade_removida": 1,
  "quantidade_restante": 4,
  "row_deletada": false
}
```

Se `quantidade_restante == 0` e não há reservas ativas em marketplace/negociações, `row_deletada: true` e a row é apagada do banco.

**Erros:**
- `400` body inválido, Idempotency-Key ausente
- `402` quantidade indisponível (retorna `disponivel`, `reservado`, `total` no body pra cliente entender)
- `403` key sem scope `inventory:write`, OU `inventario_id` pertence a outro personagem (anti-IDOR)
- `404` `inventario_id` não encontrado
- `409` item está **equipado** — desequipar pelo painel do jogador antes de remover. Item equipado bloqueia remoção pra não bagunçar build/silhueta. Também `409` se houver race condition (alguém debitou entre a leitura e o update)

---

## Códigos de status

| Status | Significado |
|-------:|-------------|
| `200` | Sucesso |
| `400` | Query/path/body inválidos, ou Idempotency-Key ausente/inválido em POST, ou personagem_id não é UUID |
| `401` | Sem `X-API-Key` ou key inválida/revogada |
| `402` | Saldo de Libras insuficiente OU quantidade de item indisponível |
| `403` | Key sem scope necessário OU anti-IDOR (row de outro personagem) |
| `404` | Recurso não existe |
| `409` | Item equipado, race condition, OU Idempotency-Key em flight (outra request paralela ainda processando — retry em 2s) |
| `429` | Rate limit excedido (geral ou write) |
| `500` | Erro interno (Idempotency-Key liberada — pode retry com mesmo UUID) |
| `503` | Falha ao reservar idempotência (raro — banco temporariamente indisponível) |

## Boas práticas

### Cache do lado cliente
- Catálogos (skills, itens, pergaminhos, maestrias) mudam pouco. Cache de 5–15 min.
- Personagem individual pode mudar a cada minuto. Cache curto (30s–60s).
- Rankings recalculam em tempo real. Cache de 1–2 min é razoável.

### Paginação
Endpoints com `limit`/`offset` retornam `total` no payload. Use pra calcular total de páginas.

### Tratamento de erros
Sempre teste `status === 200` antes de assumir payload. Erros vêm com `{ error: "...", detail?: {...} }`.

### Timeouts
Configure timeout de 10s no cliente HTTP. Endpoints como `/rankings/poder` agregam dados de centenas de personagens — pode levar 1–3s.

### Identificação do bot
Recomendado enviar `User-Agent: discord-bot-NOME/versao` pra ajudar diagnóstico.

## Exemplo de integração (Discord.js)

```js
import 'dotenv/config'
import fetch from 'node-fetch'

const ARKANDIA_API = 'https://www.ernas.com.br/api/public/v1'
const API_KEY = process.env.ARKANDIA_API_KEY

async function fetchArkandia(path) {
  const res = await fetch(`${ARKANDIA_API}${path}`, {
    headers: { 'X-API-Key': API_KEY, 'User-Agent': 'meu-bot/1.0' },
  })
  if (!res.ok) {
    const err = await res.json().catch(() => ({}))
    throw new Error(err.error ?? `HTTP ${res.status}`)
  }
  return res.json()
}

// Helper pra POSTs com idempotency. Gera UUID novo a cada chamada
// — pra retries do mesmo bot, embrulhe num retry-helper que reusa
// o mesmo idempotencyKey (ver exemplo abaixo).
import { randomUUID } from 'crypto'

async function postArkandia(path, body, idempotencyKey = randomUUID()) {
  const res = await fetch(`${ARKANDIA_API}${path}`, {
    method: 'POST',
    headers: {
      'X-API-Key': API_KEY,
      'Content-Type': 'application/json',
      'Idempotency-Key': idempotencyKey,
      'User-Agent': 'meu-bot/1.0',
    },
    body: JSON.stringify(body),
  })
  if (!res.ok) {
    const err = await res.json().catch(() => ({}))
    throw new Error(err.error ?? `HTTP ${res.status}`)
  }
  return res.json()
}

// /pagar discord:@user valor:500 motivo:"recompensa da sessão #142"
// Exemplo de POST com idempotency. Resolve o personagem do user pelo
// Discord ID, depois credita Libras com retry seguro.
//
// IMPORTANTE: a key precisa ter scope `currency:libras:write`.
client.on('interactionCreate', async (i) => {
  if (!i.isChatInputCommand() || i.commandName !== 'pagar') return

  const discordUser = i.options.getUser('discord', true)
  const valor = i.options.getInteger('valor', true)
  const motivo = i.options.getString('motivo', true)

  try {
    // 1. Resolve personagem pelo Discord ID
    const personagem = await fetchArkandia(`/personagens/discord/${discordUser.id}`)

    // 2. UUID único pra essa operação. Se você precisar retry, REUSE
    //    esse mesmo UUID — servidor devolve a resposta cacheada sem
    //    creditar de novo. Aqui gera novo a cada slash command.
    const idemp = randomUUID()

    // 3. Credita Libras. Body validado: valor em 1..100_000, descricao 1..200.
    const resp = await postArkandia(
      `/personagens/${personagem.id}/libras/creditar`,
      { valor, descricao: motivo },
      idemp,
    )

    const replay = resp.idempotency_replay ? ' (retry — operação já tinha sido processada)' : ''
    await i.reply({
      content: `✦ Creditadas **${valor.toLocaleString('pt-BR')} Libras** pra **${personagem.nome}**. Novo saldo: ${resp.novo_saldo.toLocaleString('pt-BR')}${replay}`,
    })
  } catch (err) {
    // 402 saldo insuficiente (no debitar), 403 sem scope, 404 personagem
    // não cadastrado, 429 rate limit. Mensagem genérica e segura aqui.
    await i.reply({ content: `Erro: ${err.message}`, ephemeral: true })
  }
})

// Padrão de retry com idempotency. Use isso pra operações financeiras
// que NÃO podem duplicar em caso de timeout/falha temporária.
async function postComRetry(path, body, maxTentativas = 3) {
  const idemp = randomUUID() // gerado UMA VEZ, reusado em todas as tentativas
  let ultimoErro
  for (let i = 0; i < maxTentativas; i++) {
    try {
      return await postArkandia(path, body, idemp)
    } catch (err) {
      ultimoErro = err
      // Não retry em 4xx semânticos (saldo insuf, sem scope, etc).
      if (/4\d\d/.test(err.message) && !err.message.includes('429')) throw err
      await new Promise(r => setTimeout(r, 1000 * Math.pow(2, i))) // backoff
    }
  }
  throw ultimoErro
}
```

## Mudanças & versionamento

Versão atual: **v1**.

Mudanças não-breaking (adições de campos, novos endpoints, novos query params opcionais) podem acontecer sem aviso prévio em `/v1/`.

Mudanças breaking (remoção de campo, mudança de tipo, mudança de path) só acontecem em `/v2/`. `/v1/` continua respondendo.

Quando uma versão é descontinuada, fica avisado com 90 dias de antecedência via:
- Header `Sunset: <data>` em respostas
- Comunicação por canal direto com donos de keys ativas

## Suporte

Problemas? Contate o dono da API ou abra issue no repo do Arkandia. Inclua:
- Endpoint chamado
- Query params
- Status retornado
- Header `X-RateLimit-*` se relevante
- Timestamp aproximado da request

A key revelada na criação NÃO pode ser recuperada — se perder, peça revogação da antiga e geração de uma nova.
